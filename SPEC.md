# OSINT Workspace — Технічна специфікація проєкту

Oct 9, 2026 · @Donald Duck

Універсальна веб-платформа для ОСІНТ-фахівців, аналітиків розслідувань та корпоративної розвідки: єдине робоче місце з підключенням зовнішніх інструментів, геоінтелектом, AI-аналізом та уніфікованою обробкою даних. Цей документ — технічне завдання для початку розробки (у т.ч. через Claude Code).

## 1. Огляд проєкту

OSINT-фахівці, слідчі та аналітики корпоративної розвідки щодня переключаються між десятками розрізнених сервісів (карти, супутникові знімки, Telegram, Shodan, Maltego, соцмережі, WHOIS тощо), вручну копіюючи та зводячи дані докупи. Через це втрачається час, губиться контекст і важко перевірити достовірність фактів між джерелами.

**Рішення:** універсальне, конфігуроване робоче місце (workspace) у браузері, куди фахівець підключає потрібні саме йому інструменти (через API, скрапінг або браузерну автоматизацію), а платформа зводить усі дані в єдину модель, дає спільну робочу область для збору/обробки/аналізу/верифікації та підключає AI для автоматизації рутинних дій.

**Принципи продукту:**

- **Модульність** — користувач сам вмикає/вимикає напрямки роботи (геоінт, соцмережі, корп. розвідка тощо) та підʼєднує саме ті сервіси, які йому потрібні.
- **Уніфікація** — будь-яке джерело приводиться до єдиної моделі даних, тому аналіз, пошук і перевірка працюють однаково незалежно від походження даних.
- **Розширюваність** — нові сервіси додаються через стандартизований адаптер, без переписування ядра.
- **AI-асистованість** — модель допомагає верифікувати, зіставляти й узагальнювати дані, а не замінює аналітика.

На старті цей документ не містить фінальних бізнес-рішень (монетизація, назва, юридична форма) — це технічна специфікація для початку розробки MVP з перспективою комерціалізації.

## 2. Цільова аудиторія та сценарії використання

Максимально широка ЦА всередині домену «робота з відкритими даними»: кожен з них конфігурує платформу під свій напрямок і набір інструментів.

| Аудиторія | Типові завдання |
| --- | --- |
| OSINT-фахівці / волонтерські колективи | геолокація, верифікація фото/відео, моніторинг Telegram-каналів |
| Журналісти-розслідувачі | перевірка фактів, пошук зв'язків між особами й компаніями |
| Корпоративна розвідка (due diligence) | перевірка контрагентів, бенефіціарів, репутаційні ризики |
| Служби безпеки компаній | моніторинг загроз, перевірка кандидатів/партнерів |
| Правоохоронні та оборонні аналітики | геоінт, аналіз цілей, побудова таймлайнів подій |

**Наскрізний сценарій (геоінт):** аналітик відкриває воркспейс → обирає «модуль Геоінт» → вводить координати/адресу/зображення → система одночасно підтягує дані з підключених геосервісів (карта, супутник, 360°) → аналітик рухає таймлайн і звіряє зміни місцевості у часі → зберігає знахідку як підтверджений факт у робочій області → AI пропонує перехресну перевірку з іншими джерелами.

## 3. Архітектура системи

5 шарів: джерела → адаптери → ядро → AI → UI

Шари незалежні й спілкуються через чіткі контракти: Adapter Layer ніколи не пише напряму в UI, AI-модуль читає й пише лише через ядро (БД), а UI ніколи не звертається до зовнішніх сервісів напряму — завжди через backend. Це дозволяє додавати нові сервіси чи нові AI-моделі, не чіпаючи решту системи.

## 4. Універсальна модель даних

Будь-який результат із будь-якого джерела приводиться до однієї схеми `UniversalEntity`, перш ніж потрапити в базу.

```json
{
  "entity_type": "location | person | company | ip | domain | phone | document | media",
  "entity_id": "хеш, унікальний у межах воркспейсу",
  "entity_name": "відображувана назва",
  "properties": {
    "geo": { "coordinates": [0, 0], "city": "", "country": "", "address": "" },
    "temporal": { "created": "ISO8601", "updated": "ISO8601", "observed_at": "ISO8601" },
    "digital_footprint": { "emails": [], "phones": [], "social_accounts": [], "ip_addresses": [] },
    "metadata": {
      "sources": [ { "name": "shodan", "confidence": 0.9, "last_verified": "ISO8601" } ],
      "completeness": 0.0,
      "risk_level": "low | medium | high"
    }
  },
  "relations": [ { "target_id": "...", "type": "works_at | located_in | owns | связан_с", "confidence": 0.0 } ],
  "raw_data": { "<джерело>": { } }
}
```

**Правила уніфікації:**

- `raw_data` зберігає оригінальну відповідь джерела без змін — для аудиту й повторної обробки.
- Один і той самий обʼєкт із різних джерел **зливається** за `entity_id`, а не дублюється.
- Поле `confidence` і список `sources` дають змогу бачити, скільки незалежних джерел підтверджують факт.
- Звʼязки (`relations`) зберігаються окремо від сутностей.
- Збереження йде у PostgreSQL (основні дані, JSONB для `properties`), Elasticsearch (повнотекстовий пошук) і графову надбудову (Neo4j або Apache AGE).

### 4.1 Обробка різних форматів даних, зображень та відео

Окрім структурованого JSON із API, джерела повертають і бінарні/неструктуровані дані — фото, відео, PDF, аудіо, архіви.

**Принцип:** оригінальний файл ніколи не змінюється і зберігається «як є» у S3-сумісному сховищі, а в `UniversalEntity` зі `entity_type: "media"` потрапляють лише метадані й похідні артефакти:

```json
{
  "entity_type": "media",
  "properties": {
    "media": {
      "mime_type": "image/jpeg | video/mp4 | application/pdf | ...",
      "storage_url": "s3://.../original.jpg",
      "sha256": "...",
      "phash": "...",
      "exif": { "gps": [0,0], "datetime": "...", "device": "..." },
      "duration_sec": 0,
      "resolution": "1920x1080",
      "extracted_text": "...",
      "ocr_source": "tesseract | cloud_vision"
    }
  }
}
```

**Конвеєр обробки (асинхронний, через Celery-воркери):**

1. **Прийом і валідація** — визначення реального типу файлу, перевірка на шкідливий вміст.
2. **Хешування** — SHA-256 одразу при завантаженні + перцептивний хеш (pHash/dHash).
3. **Витяг метаданих** — EXIF/GPS для фото, контейнерні метадані для відео (ffprobe).
4. **Нормалізація** — конвертація у «вітринний» формат для показу в UI.
5. **OCR** — розпізнавання тексту (Tesseract локально, або хмарний Vision API).
6. **Відео → кадри** — автоматичне вилучення ключових кадрів (ffmpeg scene-detection).
7. **AI vision-аналіз** — розпізнавання орієнтирів/об'єктів для геолокації.
8. **Reverse image search** — до Google Images / Yandex / TinEye.

## 5. Модуль геоінтелекту — синхронізовані мульти-мапи

Кілька «вікон перегляду» однієї точки місцевості (різні провайдери карт, супутник, панорама 360°), які керуються **однією спільною точкою стану** — координатами, зумом і моментом часу — і оновлюються одночасно.

### 5.1 Компонування екрана

- **Сітка панелей (2×2 або 1×3):** кожна панель — окремий «viewer», в якому користувач обирає джерело з випадного списку.
- **Спільна панель керування зверху:** поле координат/адреси, зум, компас, і **таймлайн-повзунок знизу на всю ширину екрана**.
- Кожну панель можна «відколоти» в окреме вікно — через `window.open` + `BroadcastChannel`.

### 5.2 Механізм синхронізації (map state sync)

Всі панелі підписані на єдиний **Map State Store** (Zustand/Redux на фронтенді):

```ts
interface MapState {
  center: { lat: number; lng: number };
  zoom: number;
  bearing: number;
  pitch: number;
  timestamp: string;
}
```

### 5.3 Таймлайн-повзунок

Окремий горизонтальний компонент під картами. Відмічає всі дати, на які є дані. Рух повзунка → оновлює `timestamp` → кожна панель підвантажує знімок на цю дату.

### 5.4 Провайдери та інтеграція

| Джерело | Тип даних | API/доступ |
| --- | --- | --- |
| Google Maps + Street View | карта, 360° панорами | Google Maps Platform API (платний) |
| Bing Maps (Virtual Earth) | карта, аерофото, Birds Eye | Bing Maps API |
| Sentinel Hub (Copernicus) | супутникові знімки, історичні | REST API, безкоштовний tier |
| Maxar / Planet Labs | високодетальні супутникові знімки | REST API, платно |
| Mapillary | краудсорсні 360°/вуличні фото | REST API, безкоштовно |
| OpenStreetMap | базова безкоштовна карта/геокодування | Tile API, без ключа |

## 6. Система інтеграцій (Adapter Pattern)

Кожен зовнішній сервіс підключається через адаптер, що реалізує спільний інтерфейс (`search()`, `normalize()`), і один з трьох механізмів доступу:

1. **REST/GraphQL API** — пряме підключення.
2. **Web scraping** — контрольований парсинг HTML з обмеженням частоти запитів.
3. **Browser automation** — Playwright/Puppeteer для динамічних сайтів.

**Плагінна система адаптерів:**

```
/adapters
  /shodan        (built-in, API)
  /maltego       (built-in, API)
  /google-maps   (built-in, API)
  /custom-xyz    (user-defined: config.yaml + normalize.py)
```

## 7. AI-модуль

| Тип | Приклади | Де працює | Коли використовувати |
| --- | --- | --- | --- |
| Хмарні LLM | Claude, GPT-4, Gemini | хмара, через API-ключ | складний аналіз, узагальнення, vision-аналіз |
| Локальні LLM | Llama, Mistral через Ollama | на машині користувача | приватні/чутливі дані |
| Браузерні AI-агенти | Playwright + LLM | на бекенді | автоматизація дій на сайтах без API |

**Функції AI-модуля:**

- **Верифікація/кросс-перевірка** — звести дані про одну сутність з кількох джерел.
- **Vision-аналіз** — розпізнавання обʼєктів/орієнтирів на фото для геолокації.
- **Сумаризація** — великі обсяги тексту → стислий витяг.
- **Anomaly detection** — пошук аномальних патернів у таймлайні дій.
- **Автоматизація збору** — AI-агент для типових сценаріїв збору.

## 9. Нефункціональні вимоги

- **Безпека ключів:** усі API-ключі зберігаються зашифрованими, ніколи не повертаються на фронтенд відкритими.
- **Ізоляція даних:** кожен воркспейс логічно ізольований.
- **Аудит і трасованість:** кожен факт зберігає джерело та час отримання.
- **Приватність/комплаєнс:** GDPR та профільне законодавство України.
- **Rate limiting:** кожен адаптер має власні ліміти запитів.
- **МасCALEбованість:** збір даних винесені в окремі worker-процеси.
- **Відмовостійкість:** якщо один сервіс недоступний — система продовжує працювати.
- **Локальний режим:** можливість розгорнути весь стек локально (Docker Compose).

## 11. Ключові ідеї для розвитку (від замовника)

### 11.1 Автоматичний розподіл інформації по тематичних вкладках

**Ідея:** результати пошуку мають автоматично розподілятися по тематичних вкладках бокового меню. Не потрібно вручну шукати і вставляти інформацію по різних вкладках — алгоритм має одразу розпізнати яка інформація куди має відноситись.

**Нові вкладки:**

| Вкладка | Що відображає |
|---------|---------------|
| **Особи** | Фізичні особи: ПІБ, дата народження, адреси, особисті дані |
| **Фінанси** | Фінансова інформація: рахунки, банки, закупівлі, капітал, податковий статус |
| **Підприємства** | Юридичні особи: ЄДРПОУ, форма, адреса, директор, засновники, КВЕД, статус |
| **Гео-мапи** | Адреси, координати, зображення місцевості |
| **Сутності** | Усі сутності дослідження |
